# Auditoría de configuración Cohesion — 7 octubre 2026

## Resultado

No existe paridad funcional 1:1 de las nueve pestañas. La ejecución de `scripts/audit-cohesion-settings-20261006.ts` terminó exitosa reproduciendo los defectos; no constituye aprobación del módulo. No se modificó implementación, configuración real, QuickBooks ni Cohesion.

## Hallazgos

1. **P1 — Configuración editable que no se guarda.** `app/contabilidad/configuracion/page.tsx:147-152` mantiene seis estados (`discountAccount`, `incCustomerReceivables`, `addCustomerNameMemo`, `addRevenueCenterMemo`, `ccFeeValidation`, `checkOpenOrders`) separados de `formData`. `handleSave`, líneas 283-296, serializa únicamente `formData` y `store_id`. Los controles sí cambian visualmente, pero guardar y recargar pierde los cambios; tampoco se restauran al seleccionar otra tienda. API `app/api/accounting/site-mappings/route.ts:52-61` no admite esos campos. Los memos alternativos y facilitador de impuestos suman otros 13 nodos de input sin handler (algunos se repiten en listas), entre ellos página 1061, 1092, 1278, 1318 y 1610. No hay transporte ni persistencia para dichos ajustes.

2. **P1 — Override por línea modifica la clase de toda la sucursal.** Página 1053-1055 y los demás `ClassSelect` usan `formData.qb_class` y actualizan esa misma propiedad global. La ejecución del callback original con Bell confirmó `qb_class = Bell`. Un usuario que pretende cambiar solo For Here puede reasignar todas las líneas y el encabezado de la tienda. El original capturado usa `detail.TargetClassOverrideId` y `category.TargetClassOverrideId` independientes y normalmente no seleccionados.

3. **P1 — Escrituras administrativas sin autenticación/autorización backend.** `site-mappings/route.ts:42` (PUT), 86 (PATCH alias) y 88 (POST restore) acceden al cliente privilegiado sin sesión ni comprobación de rol o tienda. `gl-accounts/route.ts:98` permite sincronizar el catálogo con el mismo patrón; `performed_by` viene del cuerpo del cliente. `middleware.ts` excluye APIs excepto Viele y no protege estos endpoints. GET tampoco verifica acceso. La allowlist limita nombres, pero no valida existencia de cuentas, coherencia número/ID bancario, tipos ni autorización de la sucursal. No se ejecutaron mutaciones anónimas.

4. **P1 — Restauraciones incompatibles.** Página 264 restaura Postmates en 12051 y 265 aplica 12100 a comisiones de Central/Broadway. API restore, líneas 114-115, usa Postmates 12050 y comisiones 51030 para todos. El dump real de Payments de Azusa selecciona explícitamente `12051 - Receivables Due from Postmates`. El mismo propósito produce configuraciones distintas según el camino; API además omite gift cards, open orders, cash on hand, tips y cogs que la restauración UI sí incluye.

5. **P2 — Ajustes contables independientes comparten una sola propiedad.** Página 1026-1041 comparte `sales_dine_in_account` entre comedor, para llevar y otros; 1090/1096 comparte `cc_fees_account` para delivery service y fee, además de merchant fees/other deductions en 1474-1485. Receivables página 1672-1687 comparte `open_orders_account` entre Accounts Receivable y Clearing. Cambiar una casilla cambia varias categorías. El dump Receivables tiene dos selects independientes, ambos sin cuenta seleccionada; la UI los rellena con 12049. El modelo plano de site-mappings no representa esos ajustes independientes.

6. **P2 — EBT deja número bancario y QB ID incoherentes.** Página 1549-1559 permite cambiar `bank_account_number` para EBT mediante AccountSelect sin actualizar `bank_account_qb_id`; el selector de banco de QuickBooks sí actualiza ambos en 949-955. También permite seleccionar cualquier cuenta GL, no solamente bancos. No se demuestra en esta subauditoría cuál identificador prevalece finalmente al publicar.

7. **P2 — Refresh Lists no refresca clases ni ubicaciones.** Página 973-982 invita a refrescar tras crear clase/ubicación, pero llama `handleSyncFromQB` (318-334), que invoca únicamente `gl-accounts` POST. Este consulta cuentas (`findAccounts`), mientras clases/ubicaciones siguen siendo arrays estáticos de página 109-121. La acción no puede cumplir lo anunciado.

8. **P2 — Catálogo parcial se presenta como sincronización exitosa.** `gl-accounts/route.ts` procesa cuentas una por una, acumula fallos y devuelve `success:true`; la UI solo muestra el número de cuentas actualizadas. Fallos al desactivar una cuenta o insertar log tampoco se comprueban. Una sincronización parcial puede conservar mapeos obsoletos sin aviso al usuario. La versión actual sí intenta desactivar cuentas inactivas: no se conserva el hallazgo anterior de que simplemente las omitía.

9. **P2 — Evidencia original insuficiente para afirmar 15 sucursales idénticas.** Las nueve capturas `cohesion_dump/live_settings/0[1-9]*.json` corresponden exclusivamente a `siteName=AZUSA`, site 2248. El script leyó todos los inputs/selects de esas capturas. Payments original tiene ocho BookTransactionDetail desmarcados; la UI muestra check verde fijo en todos (1564). Faltan asignaciones por marca de tarjeta a depósitos, depósito mínimo esperado y validación de depósitos de Cash Reconciliation. Las opciones no seleccionadas del original son reemplazadas por defaults o no tienen un control equivalente. La cantidad de nodos capturados incluye estructuras ocultas; no equivale a cantidad de campos visibles y no se usa como porcentaje de paridad.

10. **P2 — Nombres desconocidos se asignan a cuentas reales.** `lib/qb-classes-locations.ts`, función `getQBStoreRefs`, usa matching parcial bidireccional. Cadena vacía coincide con Azusa; un nombre desconocido termina con Warehouse pero cliente y banco Azusa. Prueba directa confirmó ambos resultados, además de variantes con/sin acentos. Para las 15 tiendas reales del snapshot se resolvieron referencias; ninguna cuenta configurada falta en el catálogo capturado.
